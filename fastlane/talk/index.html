Fastlane

A lean payment lane beside the EVM lane, under one consensus

October 2026

Motivation

A multi-sector chain

  • The chain becomes multi-sector. One consensus, one certificate per height.
  • Each sector trades one property for another.
  • The payment sector removes programmability to gain speed.
  • General sector: the full EVM, identical to today's EVM chain. It keeps programmability and compatibility. It trades nothing: it is the baseline.
  • Privacy sector: planned, not built. The EVM runs inside a TEE (trusted execution environment). It keeps programmability, trades some speed and gains confidentiality.
  • Payment sector: the payment lane, the subject of this talk. It keeps value transfer, trades programmability and gains speed. We are investigating it: a research prototype, measured on a small test fleet (the rest of the talk).
  • The sector idea follows the original deck: "sectors trade one property for another".
  • All sectors use the same validators and the same consensus. Each height has one certificate. Today it covers the EVM block and the lean block.

The problem

One shared lane

  • Payments share block space and fees with every other transaction.
  • Payments share one big state with every contract.
  • Each payment pays to update and hash that state.
  • Earlier measurement (old deck, local devnet, real EIP-1559): contract load kept blocks 95–100 % full; the base fee rose from 12 k to 29 M wei within 2 minutes; a simple transfer went from $0.00042 to $0.42. This is the fee market working as designed. Payments should not live in it.
  • The state of the EVM chain grows with contract activity. A real testnet snapshot is 169 GB: it no longer fits in RAM, so merklization becomes random disk I/O.

Where the time goes

The bottleneck is the state commitment, not execution

  • State root + persist ≈ 75 % of a block import computed. Execution ≈ 12 %.
  • The same shape on a real 169 GB testnet snapshot: root and disk dominate.
  • Controlled benchmark: reth v2.7.0 (harness over reth crates), i7-11700F 8C/16T, 62 GB, NVMe ext4. 1M funded accounts, 20,000 native transfers per block, 8 threads, 1 warm-up + 5 measured blocks, median per block. Two runs back to back (results/ginny-alienware-20261013-144733.json, -144750.json). All checks passed.
  • The top bar times reth's phases directly, one after another (the direct path), not the engine path, where the root overlaps execution (newPayload 196.8–199.0 ms, without persist).
  • Direct path, serial by design: 1 ecrecover (senders) 82.8 ms · 2 execute 77.9–78.5 · 3 state root 336.6–341.7 (serial incremental root, 40,000 changed accounts in a 1M-account trie) · 4 persist 151.2–151.6 (MDBX durable + static files + RocksDB, per block). Full import 651.6–662.8 ms.
  • Computed shares: run 1 (root 341.67 + persist 151.58) / 662.83 = 74.4 %, execute 11.7 %; run 2 (336.58 + 151.22) / 651.62 = 74.9 %, execute 12.1 %.
  • reth's engine path overlaps the root with execution: newPayload 196.8–199.0 ms. It hides the root; it does not remove it.
  • Sender recovery: ecrecover recovers the signer's public key from each secp256k1 signature. Same cost on both sides, ~82.5 ms per block.
  • Real state (earlier measurement, June 2026; source: docs/campaign-log.md line 60): reth 1.11, a real 169 GB testnet snapshot (block 48.75M), one 2.7M-gas block import, cold cache. Stage times from reth's own metrics: state root 27.8 ms, persistence 24.5 ms, execution 4 ms.
  • The stages overlap: the whole import took 27.5 ms, less than their sum, so no total is shown.
  • A warm re-run (trie pages cached) halved the import to 11.3 ms: about 60 % of the merkle time was cold disk I/O. reth 2.x's sparse-trie cache targets exactly this.

What we tried

Faster execution does not move the bottleneck

  • Execution is ≈ 12 % of import. Infinitely fast execution gives at most 1.14× computed.
  • UTXO is not faster for simple payments. Both models wait on signature checks.
  • Amdahl bound from the benchmark: 1 / (1 − 0.117) = 1.13×, 1 / (1 − 0.121) = 1.14×. Block-STM can only shrink the execute slice.
  • Skip the EVM (measured, 4-validator fleet, 2026-08-08): a fast path that bypassed the interpreter for native transfers. Once it emitted the required transfer logs (without them it forked against stock nodes: receipts-root mismatch), same-block A/B: newPayload 118.3 → 115.0 ms (1.03×); execute sub-metric 87.1 → 79.5 ms. The earlier 1.39–1.58× claim was mostly the missing logs, retracted. About 0.5 % of block time; kept off.
  • Old deck lever table: "Execution (Block-STM): ~1× for transfers — measured dead".
  • UTXO experiment (i7-11700F, standalone crate): UTXO and account transfers both ≈ 105k tx/s on 16 threads, both bound by signature verification (≈ 9 µs/tx parallel k256). Account contention is real but cheap for transfers (the contended work is one add). The win was isolation and a small RAM state, not UTXO.

The lean lane

Three moves

  • Each move removes one cost from the payment path.
  • Same validators, same consensus, one certificate.
  • The lane is on by a flag on all validators from height 1. With the flag off, the chain is byte-identical to upstream.
  • The lean node is a separate small process. The consensus layer talks to it through five calls (build, stage, new block, head, block bytes).

Move 1

No state commitment in the payment lane

  • The lean header has no state root, tries, logs or bloom. Its state is a flat map in RAM.
  • The EVM lane is unchanged; only prev_randao carries ch.
  • So one certificate covers the EVM block, the lean block and the whole lean chain.
  • ch = keccak(ch−1 ‖ number ‖ timestamp_ms ‖ keccak(n_txs ‖ every tx)). Every tx includes its 4 B length prefix. So every byte of the lean block is inside ch. No block carries its own commitment: every node recomputes it.
  • On Ethereum, prev_randao carries beacon-chain randomness. This chain has no beacon chain, so the field was unused (zero).
  • Consensus still votes the plain EVM block hash. The hash covers prev_randao, so the certificate covers ch; ch covers ch−1, so it covers the whole lean chain.
  • Flag off: prev_randao stays zero. A lane-on block with no lean commitment is voted Invalid.
  • Lean state: a flat nonce + balance map in RAM; durability: a block log + snapshots. The lean node keeps an append-only block log (fsync per block: 4.1 ms at 20,000 txs in the benchmark) and periodic snapshots.

Move 2

Fan-out: one signature, N payments

Jump to
  • Per 100 payments: 100 → 1 signatures, 12,200 → 2,872 B.
  • Fan-out tx (type 0x50) = 72 + 28N B: type 1 | nonce u32 4 | n_outputs u16 2 | N × (address 20 + amount u64 in gwei 8) | signature 65. In a block each tx also has a 4 B length prefix (u32): N = 1 takes 104 B of block bytes.
  • EIP-1559 native transfer ≈ 122 B: its RLP fields change length with their values (the benchmark's transfer is 115 B).
  • No chain_id (a domain tag in the signing hash binds the chain), no fee fields (fixed fee), no data or access list (no contracts).
  • Fan-out cuts per-transaction costs: signature, pool entry, envelope. Execution per payment is the same, and conflict-free by construction.

Move 3

Take work off the consensus hot path

  • Validators vote on structure only: parent link, timestamp, prev_randao = ch.
  • The vote returns at once. The lean node executes in the gap.
  • An invalid transaction is a no-op. Content never rejects a block.
  • Verified in code: the consensus layer's binding check returns Valid, then calls stage_block, which sends the block to the lean node with tokio::spawn (fire and forget). The lean node executes in its stage call. Decide promotes the staged post-state by commitment: the node already holds the bytes and the result.
  • A staged anchor costs 8–11 ms at 400 M gas per block (fleet).
  • Sender recovery (ecrecover) runs on a parallel pool, off the runtime threads. Serial ecrecover once starved admission: 0.63 vs 1.86 blocks/s.
  • A validator whose lean node is behind abstains. It never votes Invalid. A byzantine proposer can waste its own block bytes. It cannot halt or fork the lane.

Result 1 · same host, no consensus

The lean engine: 7.4× a full reth import

  • Same host, same 20,000 transfers per block, same 8 threads. One payment per signature.
  • Sender recovery (ecrecover) costs the same on both sides (≈ 82.5 ms). It is 94 % of the lean time.
  • lean headline = decode + ecrecover + execute + apply: 88.26 / 87.80 ms per block → 226,595 / 227,803 tx/s. Lean execute alone: 2.25–2.39 ms.
  • reth ecrecover + execute: 160.9–161.3 ms → 123,962–124,278 tx/s (same work, no root, no disk) → 1.8×.
  • reth engine newPayload: 196.8–199.0 ms → 100,486–101,609 tx/s (all reth optimisations, with its state root, no disk) → 2.2×.
  • reth full import (1+2+3+4): 651.6–662.8 ms → 30,174–30,693 tx/s → 7.4–7.5×. Compare with lean + block-log fsync (≈ 4.1 ms).
  • Caveats on the backup slide: the direct path is serial and persists per block; a real reth node overlaps phases and often reuses mempool sender recovery (ecrecover).

Result 2 · with consensus, 4-validator fleet

Full blocks, about 20× the EVM lane

  • Four validators, one LAN, 500 ms block pacer. Every payment-lane block is 100 % full.
  • The new limit: block bytes through consensus (≈ 4.4 MB/s), not execution.
  • EVM lane, N = 1, 150 M gas (run v02-0915-1903, 10 min): 4,377–8,419 tx/s per minute, mean ≈ 6,550; 0.81–1.57 blocks/s; blocks 51–78 % full, never full (execution/builder-bound). Re-check 2026-09-25 (run-0925-2116, lane off): 6,254–7,572 tx/s, 60–74 % full.
  • Payment lane, N = 1, 450 M (run-0925-2055, 6 min): 33,172–33,460 tx/s, 115–116 blocks/min (1.92–1.93 blocks/s), 17,307/17,307 txs per block, 100 % full.
  • N = 100, 400 M (run-0925-2042, 10 min): 143,173–148,287 payments/s, 112–116 blocks/min (1.87–1.93 blocks/s), 767/767 = 100 % full, 4/4 identical.
  • 30-min soak (run-0925-2124): 140,617–148,287 payments/s, mean 114.5 blocks/min (1.91 blocks/s), 29/29 samples 100 % full, first 10 min ≈ last 10 min (flat).
  • n = 1 per point, ±15 % run-to-run. Four heterogeneous machines, one on wifi. 143k / 6.55k ≈ 22× (computed); the worklog rounds it to ~20×.
  • Above the knee (400–450 M at N = 100) the fleet is bound by ≈ 4.4 MB/s of block bytes through consensus, not by signatures (N = 200 gives the same as N = 100) or by execution.

The price

What the payment lane gives up

The payment lane gives up

  • Light clients
  • Balance and nonce proofs
  • Certified balances: consensus certifies the transactions, not the balances
  • Receipts, logs and events
  • Standard Ethereum JSON-RPC and wallet tools
  • Contracts in the lane

It keeps

  • Certified bytes and order
  • Deterministic execution
  • Anyone can replay
  • A complete receipt is one bit: applied or no-op
  • The EVM lane keeps all of these. For the payment lane, balances, receipts and proofs must come from outside the core lane.
  • Under total-STF semantics an invalid transaction is a no-op. So the full receipt of a payment is one bit: applied or not.
  • Today a wallet can check a payment only by downloading the whole lean block (1.65–2.48 MB at the measured budgets) and rehashing it.
  • Future work 3 (slides 15–16) plans how to bring these services back with small trust: indexers, TEE attestation, ZK proofs, and the data structure the indexers use for proofs.

Future work 1 future work · open

Move money between sectors

  • Users must send money from the EVM sector to the payment sector, and back.
  • Both sectors commit under one certificate, so a transfer can be atomic per height; the mechanism is open.
  • The tension: a same-height dependency couples the two lanes, which today run in parallel.
  • Problem statement only. No design is chosen, and nothing is built.
  • Today the two lanes share no state. A balance in the payment lane and a balance in the EVM sector are separate.
  • The tension is the open question from the original deck: a transfer that depends on the other lane in the same height makes one lane wait for the other. The lanes now run in parallel, and we want to keep that.

Future work 2 future work · to measure

Bigger blocks need a better network layer

  • More transactions mean bigger blocks. The limit is block bytes through consensus: ≈ 4.4 MB/s measured.
  • Erasure-coded broadcast: the proposer sends each validator one coded piece. The validators re-share the pieces.
  • The gain grows with the number of validators: small at 4, large at 21+. to measure
  • Measured: above the knee (400–450 M gas at N = 100) the 4-validator fleet is bound by ≈ 4.4 MB/s of block bytes through consensus. N = 200 gives the same as N = 100, so signatures are not the limit.
  • The proposal is the largest part of a height. v0.2 at 300 M (period ≈ 530 ms): first part 115–150 ms, stream 116–129 ms, votes 60–120 ms, decided → anchor 76–98 ms. v0.1 at drain size: proposal stream + assemble 57 %, votes 13 %, anchor 10 %.
  • Today the proposal parts go out over gossip. With flood publish, the proposer sends each part to every peer, so its upload grows with n. On 4 validators on one LAN the gain is small. At 21+ validators across regions it should be large.
  • Not built, not measured. Erasure coding: the block becomes k data pieces plus parity pieces; any k pieces rebuild it. The code overhead gives the "1–2 × block" proposer upload.
  • Measure first on the planned 21-validator run (local 5 → local 10 → LAN → AWS 21, one zone → multi-region): flood publish on and off, and the 10 MiB value-sync cap. Expect the knee to drop at 21.
  • Compact proposals attack the same wall: the proposal carries transaction hashes, and the bodies spread before the proposal (Narwhal-style separation on the same BFT stack). It combines with erasure coding. Also not built.

Future work 3a plan · not built

Trustworthy indexers

  • The lean state transition is simple: signature checks plus balance arithmetic. That makes it a good target for proofs.
  • Signature checks dominate the proving cost, so prove per checkpoint, every K blocks.
  • A ZK-proven delayed state root brings light clients back without a trie on the validators' critical path.
  • Why: the payment lane has no state commitment. Indexers bring back balances, receipts and proofs. So users must trust indexers. The goal is to make that trust small.
  • Rung 0 (indexer phase 1, no protocol change): replay the certified blocks, index the transactions, keep a state accumulator with a checkpoint every K = 64 blocks, sign the roots. M-of-N signatures for availability, public audit. Anyone can replay, so one honest replayer detects a lie, and replay settles a dispute.
  • Rung 1: the indexer runs in a TEE. Remote attestation shows that the enclave runs the published code. Trust moves to the hardware vendor and the enclave. Fast and cheap; side channels are the known risk.
  • Rung 2: a ZK proof that the state root at checkpoint h follows from the root at h − K and the certified blocks between them. Trust: the math of the proof system. A light client verifies one proof per checkpoint. Signature checks dominate the circuit, so the proof covers K blocks at a time. Proving cost: to measure.
  • From the earlier layer plan: a proof layer (Merkle transaction root + one applied/no-op bit per transaction; inclusion proofs 1.3–3.9 KB, estimate) and an Ethereum-compatible JSON-RPC gateway over the indexers, so wallets and exchanges keep their tools.
  • The other option, validators compute a delayed state root (block h carries the root of h − K; estimate +0.6–1.5 cores and +20 GB per validator), stays "only on demand". The ZK root keeps the trie off the validators.
  • Which authenticated data structure the indexer keeps for its state: next slide.

Future work 3b plan · open choice

Which authenticated data structure?

  • The indexer needs an authenticated data structure (ADS) to give proofs. It is off the consensus hot path.
  • Many readers, one batched writer: choose for reads.
  • Avoid structures where an attacker can make paths deeper (next: Nurgle).
  • Where: the ADS lives at the indexers (slide 15), not at the validators. Validators keep the flat map. The indexer state is balances and nonces.
  • Workload: many readers (balance queries, proof requests from wallets, exchanges, light clients) and one writer that applies one batched update per checkpoint (every K blocks; K = 64 in the indexer plan). So the ADS must be read-efficient: short proofs, few lookups and disk seeks per proof, cache-friendly, cheap to serve many readers in parallel. Updates can be batched.
  • Robust against adversarial keys: in a key-prefix tree an attacker can grind keys to make a chosen path deeper (next slide, 17: Nurgle, IEEE S&P 2024).
  • Merkle-Patricia trie (Ethereum, reth): key = keccak(address); 16-ary radix tree with path compression. Deep paths and large proofs. Vulnerable to Nurgle: this mark is from the paper.
  • Jellyfish Merkle tree (Aptos/Diem style): hashed keys, path-compressed sparse tree, shorter proofs than the MPT, designed for batched versioned writes. Depth still follows shared key prefixes, so prefix grinding can deepen paths. Our inference from the attack mechanism; the paper does not test JMT.
  • Full-depth sparse Merkle tree: fixed depth (256 levels for a 256-bit key), so grinding cannot add depth. But a proof has many hashes and a lookup touches many nodes unless the tree compresses empty subtrees. Our inference.
  • Sorted Merkle accumulator (the option in our light-client design): accounts sorted by key, a Merkle tree over the positions. Depth = log2(number of accounts), independent of key prefixes, so grinding cannot deepen it. Cost: an insert shifts positions, so the indexer rebuilds per checkpoint. Our inference / design, not built.
  • Verkle tree: wide nodes, short proofs. The paper lists it as a Nurgle mitigation (flatter, shorter paths). Cost: more space per node and heavier cryptography. We mark robustness "partly": it is still keyed by prefix, so it reduces depth inflation rather than removing it (our inference).
  • Earlier measurement (old deck), write side only: we swapped reth's MPT (MDBX) for a JMT (redb) inside the EVM client. 2 h, two identical ELs on one box, same 800 tx/s load, ~26k blocks and ~4–5M accounts per lane, only the commitment differs. Windowed state-root latency: median 12.75 ms (JMT) vs 17.81 ms (MPT); mean 21.46 vs 17.30 ms; p99 85.38 vs 22.43 ms (redb flushes); 0 state-root mismatches. The leaf committed (nonce, balance) only, which flatters JMT; all state fit in RAM. Lesson: structure plus store matter, not the tree alone. This measured per-block writes, not the indexer's read workload.
  • The old deck's lever table also says "Commitment: up to 20× once state > RAM; MPT is cache-bound; JMT / SALT / dense; 4 primitives, 168 GB". We do not have its exact configuration at hand, so it is not on the slide.
  • Marks: a solid mark comes from the Nurgle paper; a dashed mark is our inference. Nothing on this slide is built or measured for the indexer.

Future work 3b · why the choice matters

The Nurgle attack (IEEE S&P 2024)

  • Grind keys that share a long prefix with a busy account. Insert them with 1-wei transfers.
  • That account's path stays deeper for good. Gas does not change: 21,000 either way.
  • For the payment lane (our inference): the validators' flat map is safe; a keccak-keyed trie at an indexer is not.
  • Source: Zheyuan He, Zihao Li, Ao Qiao, Xiapu Luo, Xiaosong Zhang, Ting Chen, Shuwei Song, Dijun Liu, Weina Niu, "Nurgle: Exacerbating Resource Consumption in Blockchain State Storage via MPT Manipulation", IEEE S&P 2024, arXiv:2406.10687.
  • Target: MPT state storage. The leaf index is keccak256(address or storage slot). The attacker picks a target leaf, preferably an active, frequently modified account.
  • Prefix grinding: brute-force identifiers whose keccak hash shares a long prefix with the target's path: 1.90 billion hashes/s on one RTX 3080.
  • Insert the crafted leaves with ordinary transactions: e.g. send 1 wei to the crafted address; for storage, e.g. an ERC20 transfer via an agent contract.
  • Effect: each shared prefix splits nodes into extension + branch nodes. A shared prefix of x nibbles pushes the target leaf to layer x + 2 (e.g. 13 nibbles → layer 15). The extra nodes persist.
  • Every later access to that account pays more: trie updates (disk and memory reads), verification (more keccak on the path to the root), in-memory node handling, persistence (more disk writes).
  • Gas does not track it: two transfers both cost 21,000 gas, but one updates 6 trie nodes and the other 9.
  • Impact: on Ethereum blocks #14.99M–#15M the added intermediate nodes amount to 1.11× all retrieved nodes (≈ 111 % more node work; model 111.2 %, < 1 % off the measurement). On testnets the authors stopped once state-modification time rose 15 % (Ethereum) and 18 % (BSC).
  • Attacker cost (paper's Table III, one-week average prices): Ethereum ≈ $11.8M, optimized ≈ $413k; BSC ≈ $198k, optimized ≈ $7.0k; Optimism ≈ $40 (GPU part $39.6: 33 RTX 3080 × 12 h). The optimized variant costs 3.5 % for 54.66 % of the impact.
  • Confirmed by six mainstream blockchains (bounties paid). Per the paper, 588 Ethereum-compatible and 153 Polkadot-compatible platforms are affected.
  • Mitigations in the paper: (i) Verkle tree: flatter, shorter paths; costs more space per node. (ii) Trimming historical state (EIP-4444): costs full historical verification. (iii) A gas mechanism that charges for MPT node changes: may open new attack vectors.
  • Why it matters for the payment lane (our inference): the lane's validators keep a flat hash map, not a trie, so the attack does not target consensus. An indexer that builds a keccak-keyed trie inherits it. Fan-out makes crafted recipients cheap: 28 B and one tiny payment each, many per signature. So the indexer's ADS should have a depth independent of key prefixes (e.g. a sorted accumulator or a fixed-depth tree), and/or the lane should price account creation.
  • The trie figure is a schematic: real MPT branch nodes have 16 children and the chain is drawn shortened.

Summary

Each move costs something

  • Lean engine: 7.4× a full reth import on one host. Fleet: 143k–148k payments/s, every block full.
  • Each move costs something. Each future-work item buys it back. plan
  • A block import pays mostly for the state commitment, not for execution. The payment lane drops the state commitment from its own blocks (the EVM lane keeps its full header), fans out payments and votes on structure only.

How the payment lane persists data

  • No database, no trie. Live state is a flat map in RAM.
  • The node appends each decided block to a log and fsyncs it. Every 1024 blocks, it writes the whole map to a snapshot.
  • The price: the state must fit in RAM (≈ 130 MB at 1M accounts).
  • Code (lean node, v0.3-dev, crates/lean-lane-node/src): chain.rs BlockLog::append (record = [len u32][block payload][len u32], then file.sync_data unless --no-fsync), BlockLog::replay (stops at the first record whose bounds or trailing len do not check, truncates there); state.rs write_snapshot (commitment, number, timestamp, count, then per account address 20 B + nonce u64 + balance u128 = 44 B; temp file, sync_all, rename to snapshot-N.bin); node/commit.rs (the one append both commit paths use); node/mod.rs LaneNode::open (newest snapshot not ahead of the log, replay the tail).
  • Live state = HashMap address → (nonce, balance). The log stores blocks, not state. An in-memory index (block number → file offset) serves old blocks to peers.
  • Snapshot every 1024 blocks (--snapshot-every, default 1024; 0 = never, replay from genesis). Size: 56 B + 44 B per account ≈ 44 MB at 1M accounts.
  • Restart: newest snapshot not ahead of the log → replay the blocks after it → head. A torn tail is truncated. If the log lost its tail (only possible with --no-fsync; snapshots are always fsynced), the node falls back to an older snapshot and pulls the missing blocks from peers. The certificate binds the bytes: a liveness cost, never a safety cost.
  • Numbers: benchmark lean-lane-bench/bench/native-transfer (README + results/ginny-alienware-20261013-*.json), 1M accounts, 20,000 txs per block, i7-11700F, NVMe ext4. Lean block-log append + fsync 4.06–4.08 ms per block; reth persist (MDBX durable + static files + RocksDB) 151.2–151.6 ms per block. reth writes changed accounts and trie nodes into a B-tree (random I/O); its on-disk state is always current. Lean's on-disk state is current only at snapshots.
  • Trade-offs: state must fit in RAM (≈ 130 MB at 1M accounts, ≈ 1 GB at 10M). No disk-side queries of old balances: that is an indexer job. The snapshot is written on the commit path with blocking I/O: fine at fleet sizes; moving it to a background thread is an open item before 10M+ accounts.
  • The figure is a schematic: block positions are not to scale.

Block bytes → payments per second

  • A 2 MB block at 2 blocks/s is 4 MB/s, close to the measured ≈ 4.4 MB/s wall.
  • Fan-out gains flatten after N ≈ 10: bytes per payment fall from 104 to ≈ 28.8.
  • Computed: txs per block = floor(2,000,000 / (72 + 28N + 4)); payments/s = txs × N × 2.
  • N = 1: 104 B → 19,230 txs → 38.5k/s. N = 5: 216 B → 9,259 → 92.6k/s. N = 10: 356 B → 5,617 → 112.3k/s. N = 100: 2,876 B → 695 → 139.0k/s.
  • The measured N = 100 point (143k–148k at 400 M gas) sits near this line.

Benchmark fairness caveats

  • ecrecover (sender recovery) dominates lean. Same library (libsecp256k1), same threads. A real reth node often recovers senders at mempool time and reuses them.
  • reth's direct path is serial. A real node overlaps ecrecover, execution and root (engine path). "Full import" is an upper bound for one block.
  • Persist is per block on the direct path. A real node persists in background batches.
  • The engine path uses more threads (prewarm, proof workers, sparse trie). lean uses one pool of 8.
  • Allocators differ: reth on jemalloc, lean on the system allocator.
  • Not the same work: reth runs full EVM semantics (fees, system contracts, receipts). lean runs a payment-only transition. That is the point of the lane.
  • Small samples: 5 measured blocks per run, two runs. Treat differences under ≈ 10 % as noise.
  • Not measured: consensus, networking, mempool, RPC, block building. The page cache is warm.
