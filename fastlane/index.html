Walk-through 1 / 4

A dedicated payment lane beside the EVM lane

  • One BFT consensus orders both lanes at every height.
  • The same validators vote once per height. One certificate covers both lanes.
  • The EVM lane runs a full EVM client.
  • The payment lane runs a small native engine, the lean node. It accepts native transfers only.
  • Agreement is not partitioned. So there is no cross-shard atomicity problem.

EVM lane

  • Full EVM client, driven over the Engine API
  • State in a Merkle–Patricia trie, with receipts and logs
  • Any transaction: contract calls and transfers
  • EIP-1559 native transfer: about 122 bytes

Payment lane

  • Lean node, driven over a five-verb JSON-RPC interface
  • State is a flat map: one nonce and one balance per account
  • Native transfers only: one signature pays $N$ recipients
  • Blocks form a hash chain. The head of the chain is the commitment $c_h$.

Step through one height

The lean block holds

Validators execute every lean block.

  • The vote checks structure only: parent link, timestamp, commitment.
  • The lean node executes the block while the votes arrive.
  • The vote does not wait for the result.

An invalid payment is a no-op.

  • It does not reject the block. The other payments apply.
  • A bad proposer can waste its own block space.
  • A bad proposer cannot halt or fork the payment lane.

Walk-through 2 / 4

Transaction format: from Ethereum transfers to fan-out

  • The EVM lane carries EIP-1559 native transfers. One transfer pays one recipient. It is about 122 bytes.
  • The payment lane carries one transaction type: 0x50, fan-out. One signature pays $N$ recipients.
  • Size: $72 + 28N$ bytes. Each recipient adds 28 bytes: a 20-byte address and an 8-byte amount.
Jump to

    EIP-1559 native transfer · ≈ 122 B

    Fan-out 0x50 · $72 + 28N$ B

    What the format drops

    • chain_id. A domain tag in the signing hash binds the chain. The transaction does not carry it.
    • Fee fields and gas_limit. The fee is fixed. The transaction does not bid.
    • data and access list. The payment lane has no contracts.
    • value as u256 in wei. The amount is a u64 in gwei.
    • Variable-length nonce. The nonce is a fixed u32.
    • RLP list header. The layout is fixed. The only length field is n_outputs.

    Walk-through 3 / 4

    Block headers and the prev_randao hook

    • The EVM chain activates every Ethereum fork from genesis.
    • So its block header is the standard post-Prague Ethereum header: 21 fields.
    • On Ethereum, prev_randao carries beacon-chain randomness. This chain has no beacon chain. The field is unused: zero.
    • Hover, tap or tab to a field for its role.
    Payment lane

      Lean header: 52 bytes

      • parent commitment 32 | number u64 | timestamp_ms u64 | n_txs u32
      • Then the transactions, each with a length prefix.
      • The commitment chains to the parent:

      $c_h = \mathrm{keccak}\big(c_{h-1} \,\|\, h \,\|\, t_h \,\|\, \mathrm{keccak}(\mathrm{txs}_h)\big)$

      $h$ = number · $t_h$ = timestamp_ms · txs = the transaction section

      • No block carries its own commitment. Every node recomputes $c_h$ from the bytes.

      The binding

      • With the payment lane on, the proposer sets prev_randao $= c_h$.
      • Consensus certifies the plain EVM block hash, as before.
      • The EVM block hash covers prev_randao. So one certificate commits to exactly one lean block.
      • The lean header holds $c_{h-1}$. So the certificate also commits to the whole lean chain.
      • With the payment lane off, prev_randao stays zero. The chain is byte-identical to upstream.

      What the lean header does not have

      • state_root
      • transactions Merkle root
      • receipts_root
      • logs_bloom
      • gas_limit, gas_used, base_fee
      • beneficiary

      The transaction hash in $c_h$ is a flat keccak over the transaction bytes, not a Merkle root.

      Walk-through 4 / 4

      The trade-off, and the indexer we need

      The lean header has no state root, no receipts root, no log bloom and no transaction Merkle root.

      What the payment lane gives up

      • No balance or nonce proofs.
      • No light-client support.
      • Consensus certifies the transactions. It does not certify the balances they produce.
      • No receipt or event commitments.
      • No standard Ethereum wallet JSON-RPC.

      What it keeps

      • Block bytes and their order are certified.
      • Execution is deterministic.
      • Anyone can replay the chain from the certified bytes.
      • A complete receipt is one bit: applied or no-op.

      So balances, receipts, history and proofs must come from indexers.

      Question for the meeting

      Do indexers need their own full consensus, or something weaker?

      Proposal · not a measured result
      • Agreement has two parts: order the input, then compute the output.
      • The chain's consensus already orders the input. That is the hard part.
      • An indexer's output is a deterministic function of the certified input.
      • So indexers need no BFT protocol among themselves.
      • One honest replayer is enough to detect a wrong answer.
      • M-of-N signatures over the same output give availability and convenience.
      • A disagreement is objective evidence. Replay settles it.

      Four options: trust against protocol change

      ← trust operators, no protocol changetrust consensus only, more protocol change →
      Recommendation · proposal
      1. Start with (b): M-of-N indexers and a public replay audit. No protocol change.
      2. Fold (c) into the next coordinated format change.
      3. Keep (d) for when users need trustless balances.

        Interactive 3 · a bug that looked like a design limit

        The drift

        For a day every run slowed down minute by minute while blocks stayed 100 % full and pools stayed deep. The cause was in the lean node: when asked for block bytes by a commitment it had not indexed yet, it scanned its whole log backwards, reading and hashing every block. The consensus layer asks about once per height, so each height cost more than the last. Both runs below use the same consensus build, the same 225 M budget and $N=100$. The only change is that the scan stops at the index floor.

            Proposals

            What comes next

            1 · Proofs for light clients, without putting Merkle work back on validators

            The lane drops the trie and the receipts, so today a wallet can check a payment only by downloading the whole lean block and re-hashing it (1.65–2.48 MB at the measured budgets). The block bytes are already certified, so the plan builds proofs from them in three phases. Figures marked est. are design estimates, not measurements.

            Phase 1 · no protocol change

            Attested indexer

            • Replays certified blocks, indexes transactions, keeps a state accumulator with a checkpoint every $K=64$ blocks, signs roots.
            • Anyone can replay and audit it; balances are attested, not proven.
            • ~2–3 weeks est.
            Phase 2 · format change

            Merkle root + one-bit receipts

            • The transaction hash inside $c_h$ becomes a Merkle root over the framed transactions.
            • Under total-STF a complete receipt is one bit per transaction ("applied" or "no-op").
            • Inclusion proofs 1.3–3.9 KB, 420–1300× smaller est.; vote path +3 % est.
            Phase 3 · only on demand

            Delayed state root

            • Block $h$ carries the state root of $h-K$, computed in the background and checked at vote time.
            • Account proofs with no trusted party.
            • +0.6–1.5 cores and +20 GB per validator est.; ~4–6 weeks est.

            2 · A clean integration surface

            The code was written fast under benchmark pressure. An audit of all three parts gives the cut:

            PartTodayTarget est.What goes
            Consensus-layer delta (Rust)+6,872 lines~2,300timing instrumentation, an experiment knob, unrelated store work (own PR), five test traits collapsed to one
            Consensus-layer delta (scripts, docs)+5,245 lines~800fleet tooling moves out; one integration guide
            Lean node repository (Rust)~17,000 lines~5,000the log-scan fallback (full index from replay), stdout diagnostics, dead modes, a borrowed load generator, overlapping concurrency guards

            3 · Open measurement questions

            • A mild decline over 30-minute runs at constant fullness: at 400 M, ~113.6 blocks/min over the first ten minutes against ~104.5 over the last ten. The log scan is ruled out (zero scans throughout).
            • 450 M slides within ten minutes (114.38 → 98.44 blocks/min), so the knee at 2 blocks/s is between 400 and 450 M.
            • The 60 ms wait the lean node allows for a stage that hasn't arrived yet is sized from an estimate; the arrival stamps now in the logs should retune it.
