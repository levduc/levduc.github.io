Fundamental concepts

Confidentiality and authentication are different goals

  • Encryption hides content. A MAC binds content to a key.
  • Having one gives you nothing about the other.
  • Menezes V5 p.4. The examples named there are AES-CBC for encryption and HMAC for the MAC.
  • The source then asks: what if both are required? It adds, in parentheses, "which is more often the case than not". That is the motivation for the whole module.

Fundamental concepts

Encryption alone does not authenticate

  • In CTR mode the ciphertext is the plaintext XOR a keystream.
  • So flipping a ciphertext bit flips exactly the matching plaintext bit.
  • Bob has no way to notice. This is why a MAC is a separate requirement.
  • This slide is not in the source; it is the concrete reason behind the source's framing on p.4. The attack uses the CTR structure from Menezes V5 p.11: $C_i = \mathrm{AES}_k(J_i) \oplus M_i$, so $M_i = \mathrm{AES}_k(J_i) \oplus C_i$.
  • The attack needs no key and no knowledge of the plaintext. If the adversary knows the plaintext she can set it to any value she wants, by XORing in the difference.
  • The same malleability is what makes the IV-reuse attack later in this deck so damaging.

Generic composition 1 of 3

Encrypt-and-MAC: the tag is computed over the plaintext

  • Alice sends $(c, t)$ with $c = E_{k_1}(m)$ and $t = \mathrm{MAC}_{k_2}(m)$.
  • Bob decrypts $c$, then checks $t$ against the recovered $m$.
  • Not secure as a generic method.
  • Menezes V5 p.5. The source's reason: "the tag $\mathrm{MAC}_{k_2}(m)$ might leak some information about $m$."
  • Spelled out: a MAC is required to be unforgeable, not to hide its input. Most practical MACs are deterministic functions of $(k,m)$, so $m_1 = m_2 \Rightarrow t_1 = t_2$. An adversary who sees two transmissions learns whether the two plaintexts were equal, which already breaks semantic security.
  • Bob also decrypts before he authenticates, so a forged $c$ reaches his decryption routine. That is a second, separate problem.

Generic composition 3 of 3

Encrypt-then-MAC: the tag is computed over the ciphertext

  • Alice sends $(c, t)$ with $c = E_{k_1}(m)$ and $t = \mathrm{MAC}_{k_2}(c)$.
  • Bob verifies first, and decrypts only if the tag checks out.
  • Proven secure whenever $E$ and the MAC are each secure.
  • Menezes V5 p.6, which states the proof exists and the condition it needs.
  • Why the leak from Encrypt-and-MAC disappears: the tag is now a function of $c$, and $c$ already hides $m$. Equal plaintexts encrypted under different IVs give different ciphertexts, hence different tags.
  • Why verify-first matters: the decryption routine never runs on attacker-chosen input, so it cannot be used as an oracle. This is the property that padding-oracle attacks exploit when the order is reversed.
  • $k_1$ and $k_2$ must be independent keys.

Generic composition · summary

Only one of the three is generically secure

  • "Generic" means: secure for every secure $E$ and MAC, not just some.
  • Encrypt-then-MAC is the one to reach for.
  • Encrypt-and-MAC and Encrypt-then-MAC are Menezes V5 p.5–6. MAC-then-Encrypt is not in the source deck; it is added here because it is the third classical composition and the one used by older TLS CBC ciphersuites.
  • MAC-then-Encrypt is marked "~" rather than "✗": it is secure for some encryption modes but has no generic proof, and its real-world failures (padding oracles) come from Bob decrypting before he authenticates.
  • The classification of the three compositions is due to Bellare and Namprempre (2000) and Krawczyk (2001). That attribution is this deck's addition, not the source's.

Fundamental concepts

What "AE-secure" asks for

  • Confidentiality: she cannot tell which plaintext she got.
  • Integrity: she cannot produce a new valid ciphertext.
  • Menezes V5 p.8, stated there as a two-part definition.
  • The condition $c \notin \{c_1,\dots,c_\ell\}$ is what makes the definition non-trivial: replaying a pair she already holds is not a forgery. She must produce a ciphertext she has never been given.
  • Note it is ciphertext integrity, not plaintext integrity. Forging a fresh ciphertext that decrypts to an already-seen plaintext still counts as a break.
  • Ciphertext integrity plus CPA security together imply security against chosen-ciphertext attack. The source does not state this; it is the standard reason the definition is framed this way.

Fundamental concepts

Some data must be authenticated but not encrypted

  • Routing and version fields must stay readable, but must not be changeable.
  • Schemes that support this take additional authenticated data, $A$.
  • Menezes V5 p.7, which calls it "header" data and notes that many special-purpose AE schemes allow authenticating it without encrypting it.
  • SP 800-38D calls it AAD. AES-GCM also calls it the encryption context in some API documentation.
  • Concrete case: a packet header has to be read by a router that holds no key, yet an adversary must not be able to redirect the packet by rewriting it.
  • Length limits from SP 800-38D §5.2.1.1: $\mathrm{len}(A) \le 2^{64}-1$ bits.

AES-GCM

CTR mode for secrecy, GMAC for the tag

Menezes V5 p.9 onwards. AES-GCM was designed by David McGrew and John Viega in 2004 and adopted as NIST SP 800-38D in 2007.

AES-GCM

Two parts, one key

  • CTR mode turns AES into a stream cipher and encrypts the payload.
  • GMAC is a custom MAC built from arithmetic in $\mathrm{GF}(2^{128})$, and produces the tag.

Designed by David McGrew and John Viega, 2004. NIST standard SP 800-38D, 2007.

  • Both parts are driven by the same AES key $k$ and the same nonce.
  • This is not a generic composition: GMAC alone is not a secure MAC.
  • Menezes V5 p.10 for the designers, the date and the standard number.
  • The last bullet matters and is this deck's emphasis: $f_A(H)$ on its own is forgeable (see the security slides). GCM is secure because of how the two parts are glued, not because each is independently strong.
  • Key sizes: 128, 192 or 256 bits (Menezes V5 p.12 and p.20). The block is always 128 bits, and so is $H$.

AES-GCM · encryption

CTR mode encrypts counters, not data

  • $C_i = \mathrm{AES}_k(J_i) \oplus M_i$, one block at a time.
  • The columns do not depend on each other, so this parallelizes.
  • Decryption runs the same circuit: $M_i = \mathrm{AES}_k(J_i) \oplus C_i$.
  • Menezes V5 p.11. Both directions are on that page; they are the same computation because XOR is its own inverse.
  • $\mathrm{AES}^{-1}$ is never used (Menezes V5 p.12, note 5). An implementation only needs the forward direction, which halves the code and the table footprint.
  • Because it is a stream cipher, the ciphertext is exactly as long as the plaintext — no padding, so no padding oracle.
  • The cost of that: the ciphertext is malleable, which is the attack on slide 4. CTR gives confidentiality only; the tag is what adds integrity.

AES-GCM · encryption

Where the counters come from

  • $J_0 = IV \,\|\, 0^{31} \,\|\, 1$ when the IV is 96 bits.
  • Encryption starts at $\mathrm{inc32}(J_0)$ — counter 2, not counter 1.
  • $J_0$ is held back to mask the tag.
  • $J_0$ construction: Menezes V5 p.11 and p.14; SP 800-38D §7.1 step 2 ("If len(IV)=96, then let $J_0 = IV \| 0^{31} \| 1$").
  • Encryption starting at $\mathrm{inc32}(J_0)$: SP 800-38D §7.1 step 3, "Let $C = \mathrm{GCTR}_K(\mathrm{inc32}(J_0), P)$". Menezes writes the same thing as $J_i \leftarrow J_{i-1} + 1$ starting from $J_0$.
  • If the IV is not 96 bits, SP 800-38D computes $J_0 = \mathrm{GHASH}_H(IV \| 0^{s+64} \| [\mathrm{len}(IV)]_{64})$ instead. The 96-bit case is the only one where $J_0$ is formed directly, which is why it is recommended. Menezes covers only the 96-bit case.
  • $\mathrm{inc32}$ increments the rightmost 32 bits modulo $2^{32}$ and leaves the IV part untouched (SP 800-38D §6.2).

AES-GCM · encryption

Why the payload stops at $2^{32}-2$ blocks

  • The counter is only 32 bits wide, and $J_0$ takes one value.
  • The standard caps the plaintext so the counter can never wrap back to $J_0$.
  • A wrap would repeat a keystream block — the same break as reusing an IV.
  • Menezes V5 p.11 states $u \le 2^{32}-2$ directly. SP 800-38D §5.2.1.1 states the bound as $\mathrm{len}(P) \le 2^{39}-256$ bits.
  • These agree. $(2^{39}-256)/128 = 2^{32}-2$, since $2^{39}/2^7 = 2^{32}$ and $256/128 = 2$. computed — the division is this deck's arithmetic, both endpoints are sourced.
  • $2^{32}-2$ blocks is about 64 GiB per invocation, so the limit does not bite in practice. It is a correctness bound, not a performance one.
  • Other bounds from the same section: $\mathrm{len}(A) \le 2^{64}-1$ and $1 \le \mathrm{len}(IV) \le 2^{64}-1$ bits.

AES-GCM · encryption

Six things to remember about CTR

  • It is a stream cipher. The keystream depends only on the key and the counters, never on the data.
  • Different IVs give different ciphertexts for the same plaintext, as with CBC.
  • The IV must never repeat under one key. The standard says this is hard to achieve in practice, and it is the sharpest edge in the whole mode.
  • It parallelizes, unlike CBC encryption: every block is independent.
  • $\mathrm{AES}^{-1}$ is never needed, in either direction.
  • The key may be 128, 192 or 256 bits. The block, and $H$, stay 128 bits.
  • Menezes V5 p.12, all six, in the source's own order.
  • Point 3 is developed fully on the IV-reuse slide near the end of this deck.
  • Point 1 is why CTR is malleable (slide 4): the attacker can predict exactly how a ciphertext edit moves the plaintext, without knowing the keystream.

AES-GCM · the tag

Arithmetic in $\mathrm{GF}(2^{128})$

What it means to multiply two 128-bit blocks

Menezes V5 p.13. The field is named after Évariste Galois. GMAC needs multiplication of blocks; the next two slides define it and work one all the way through.

GF(2^128)

A block is a polynomial

  • Bit $a_i$ is the coefficient of $x^i$, so $a_0$ is the constant term.
  • Coefficients live in $\mathbb{Z}_2$: addition is XOR, and $1+1=0$.
  • Menezes V5 p.13: $a = a_0a_1a_2\ldots a_{127}$ maps to $a(x) = a_0 + a_1x + a_2x^2 + \cdots + a_{127}x^{127} \in \mathbb{Z}_2[x]$.
  • Watch the bit order. The first bit is the lowest power, which is the reverse of how integers are normally written. This "bit-reflected" convention is a well-known source of implementation bugs in GCM.
  • Adding two blocks is plain XOR, because coefficients add mod 2. It is multiplication that needs the field.

GF(2^128)

Multiply, then reduce — worked all the way through

  • $c = a \cdot b$ means $c(x) = a(x)\,b(x) \bmod f(x)$.
  • Shown in the toy field $\mathrm{GF}(2^4)$ so every step fits; GCM uses the same recipe.
  • Definition and the real modulus: Menezes V5 p.13, $f(x) = 1 + x + x^2 + x^7 + x^{128}$.
  • The worked example is this deck's own, in $\mathrm{GF}(2^4)$ with $f(x) = 1 + x + x^4$, because the 128-bit case cannot be shown by hand. computed
  • Full check: $a(x)b(x) = (1+x+x^3)(1+x) = 1 + x + x + x^2 + x^3 + x^4$. The two $x$ terms cancel, leaving $1 + x^2 + x^3 + x^4$. From $f(x)=0$ we get $x^4 = 1+x$, so the sum becomes $1 + x^2 + x^3 + 1 + x = x + x^2 + x^3$ after $1+1=0$. In bits, $a_0a_1a_2a_3 = 0111$.
  • Why "mod $f$": the product of two degree-$<$128 polynomials can reach degree 254, so it must be folded back into 128 bits. $f$ is irreducible, which is what makes the result a field — every nonzero block has an inverse, and a nonzero polynomial has at most its degree many roots. That last fact is what the forgery bound rests on.
  • Hardware does this with the PCLMUL instruction (Menezes V5 p.20, point 3).

Recap

GMAC packs the message into one polynomial

  • Each 128-bit block of $A$ becomes one coefficient; the length block $L$ is the last one.
  • The secret evaluation point is $H = \mathrm{AES}_k(0^{128})$.
  • The tag is $t = \mathrm{AES}_k(J_0) \oplus f_A(H)$.
  • Menezes V5 p.14. $f_A(x) = A_1x^{v+1} + A_2x^{v} + \cdots + A_{v-1}x^{3} + A_vx^{2} + Lx$, over $\mathrm{GF}(2^{128})$.
  • Note the lowest term is $Lx$, not $L$: every term carries at least one factor of $x$. Degree is $v+1$ where $v$ is the blocklength of $A$.

AES-GCM · the tag

Evaluating $f_A(H)$ without ever forming a power

  • Nesting turns powers of $H$ into one multiply per coefficient.
  • For blocklength $v$: $v$ additions and $v+1$ multiplications.
  • Menezes V5 p.15, including the $v=3$ worked example and the general count.
  • The source writes it as $f_A(H) = ((((((A_1 \cdot H) + A_2) \cdot H) + A_3) \cdot H) + L) \cdot H$. Note the final $\cdot H$: it is there because the lowest term is $Lx$, not $L$, so every term carries a factor of $H$.
  • Additions are free in hardware (XOR). The multiplications are the cost, which is why PCLMUL matters so much — see the performance slide.
  • The multiplication count is also the forgery bound. $v+1$ multiplications, degree $v+1$, at most $v+1$ roots. The same number shows up in all three places.

Security argument · the simplified tag

First attack: guess the tag outright

  1. 1Drop the one-time pad for now and consider the simplified tag $t' = f_A(H)$. It is a single 128-bit value.
  2. 2She submits one guess. Exactly one of the $2^{128}$ values is accepted, so $\Pr[\text{success}] = 1/2^{128}$.
  3. 3A rejected guess teaches her nothing: the verifier answers only accept or reject, and every other value stays equally likely.
  • Menezes V5 p.16, first bullet, which states the $1/2^{128}$ figure. The reasoning is spelled out here.
  • This is the baseline every MAC must beat: with a 128-bit tag, blind guessing cannot do better than $2^{-128}$ per attempt. The next slide shows that attacking $H$ instead does better — by a factor of up to $v+1$.
  • Strictly, $t'$ is uniform over the $2^{128}$ values only when $H$ is; here $H = \mathrm{AES}_k(0^{128})$ is modelled as uniform. The source states the bound without the qualifier.
  • Over $q$ verification attempts the chance grows to about $q/2^{128}$, which is why implementations cap failed attempts in some settings.

Security argument · the simplified tag

Guessing $H$ succeeds with probability at most $\frac{v+1}{2^{128}}$

  1. 1Strip the one-time pad and look at $t' = f_A(H)$ alone. The adversary wants $t'$ for a message $A$ of her choice, without knowing $H$.
  2. 2She picks one guess $H'$ and outputs $t' = f_A(H')$. She wins exactly when $f_A(H') = f_A(H)$.
  3. 3Put everything on one side: $g(x) = f_A(x) + f_A(H')$. In characteristic 2 subtraction is addition, so she wins iff $g(H) = 0$.
  4. 4$g$ is not the zero polynomial and $\deg g = v+1$: adding the constant $f_A(H')$ changes only the $x^0$ term, and the leading term $A_1x^{v+1}$ survives.
  5. 5A nonzero degree-$d$ polynomial over a field has at most $d$ roots. So at most $v+1$ of the $2^{128}$ elements are roots of $g$.
  6. 6$H = \mathrm{AES}_k(0^{128})$ is unknown and uniform, and she chose $H'$ before seeing it. So $\Pr[g(H) = 0] \le \dfrac{v+1}{2^{128}}$.
  • Menezes V5 p.16 states the bound; this slide is the derivation spelled out.
  • Why "at most". A nonzero degree-$d$ polynomial over a field has at most $d$ roots in that field; $g$ may well have fewer than $v+1$. So the count of winning $H$ values is an upper bound, which is exactly what a security claim needs.
  • Why the leading term survives. $f_A(H')$ is a constant, i.e. a degree-0 term. $f_A(x)$ has no constant term at all (its lowest term is $Lx$), so $g(x) = A_1x^{v+1} + \cdots + Lx + f_A(H')$. Nothing can cancel $A_1x^{v+1}$, assuming $A_1 \ne 0$.
  • Order of quantifiers matters. She commits to $H'$ first, then $H$ is drawn. If she could pick $H'$ after seeing $H$ the probability would be 1. This is why the bound is over the randomness of $H$ (i.e. of the AES key).
  • Compare: guessing the 128-bit tag directly succeeds with probability $1/2^{128}$ (Menezes V5 p.16). Guessing $H$ is better by a factor of up to $v+1$, because many different $H$ values can produce the same tag for this particular $A$. Longer messages give the adversary more roots to hit.

Security argument · the simplified tag

Third attack: one valid pair, and the guessing stops

  • $A$ and $t'$ are both known. $H$ is the only unknown.
  • That makes it an equation to solve, not a value to guess.
  • Menezes V5 p.16, third bullet: "if the adversary sees a single valid message-tag pair $(A, t')$, she can solve the polynomial equation $f_A(H) = t'$ for $H$."
  • This is the punchline of the whole security slide. The first two attacks are bounded by $1/2^{128}$ and $(v+1)/2^{128}$ — both negligible. This one is not a probability at all. It is why the simplified tag $t' = f_A(H)$ cannot be used as a MAC.
  • Root-finding over $\mathrm{GF}(2^{128})$ runs in polynomial time (Cantor–Zassenhaus and friends). The degree is $v+1$, so she gets at most $v+1$ candidate values for $H$ and can test each against the pair she holds. That candidate count is this deck's note, not the source's.
  • Nothing about AES is broken here. $H = \mathrm{AES}_k(0^{128})$ is still unknown as a function of the key — but she does not need the key, only $H$ itself.

Security argument · the fix

Hide the polynomial value behind a one-time pad

  • $t = \mathrm{AES}_k(J_0) \oplus f_A(H)$ — the real GMAC tag.
  • $\mathrm{AES}_k(J_0)$ is a second secret, fresh per nonce.
  • She sees $t$, never $f_A(H)$, so there is no equation in $H$.
  • Menezes V5 p.16, last bullet: "To circumvent the aforementioned attack, a second secret $\mathrm{AES}_k(J_0)$ is used to hide $t'$ ... The secret $\mathrm{AES}_k(J_0)$ serves as a one-time pad for $t'$."
  • "One-time" is meant literally. The pad depends on $J_0$, which depends on the IV. A fresh IV gives a fresh pad; a repeated IV gives the same pad twice, and XORing two such tags cancels it exactly. That is the attack three slides on.
  • This is the Carter–Wegman construction: a universal hash of the message, masked by a pseudorandom pad. The attribution is this deck's addition.
  • So the three attacks end: guessing the tag, $1/2^{128}$; guessing $H$, at most $(v+1)/2^{128}$; solving for $H$, blocked by the pad — provided the IV never repeats.

AES-GCM · the full scheme

Encryption and authentication, side by side

  • The tag covers $A$ and $C$ — this is Encrypt-then-MAC in spirit.
  • $H$ and the pad both come from the same key $k$.
  • Menezes V5 p.18, all five steps, including $L = L_A \| L_M$ as 64-bit lengths.
  • Note the order in the source: encryption first, then authentication over the resulting $C$. GCM authenticates the ciphertext, not the plaintext, which is the composition shown to be generically secure on slide 7.
  • $H = \mathrm{AES}_k(0^{128})$ is the same for every message under a given key. Only the pad $\mathrm{AES}_k(J_0)$ changes per nonce. Implementations precompute $H$ and its multiples once per key.
  • Why $L$ is included at all: without it, messages that differ only by trailing structure could collide. The length block binds $|A|$ and $|M|$ into the tag.

AES-GCM · the full scheme

One polynomial over the header and the ciphertext

  • $A$ takes the top exponents, then $C$, then $L$ on $x^1$.
  • Degree $u+v+1$, so the forgery bound becomes $(u+v+1)/2^{128}$.
  • Menezes V5 p.18, the note at the bottom: $f_{A,C}(x) = A_1x^{u+v+1} + A_2x^{u+v} + \cdots + A_vx^{u+2} + C_1x^{u+1} + C_2x^{u} + \cdots + C_ux^{2} + Lx$.
  • The bound on slide 22 was stated for $f_A$ with degree $v+1$. The same argument applies verbatim to $f_{A,C}$ with degree $u+v+1$ — longer messages, slightly weaker bound. computed: the source states the bound only for the $f_A$ case.
  • SP 800-38D builds the same value as $\mathrm{GHASH}_H(A \| 0^v \| C \| 0^u \| [\mathrm{len}(A)]_{64} \| [\mathrm{len}(C)]_{64})$, where the zero strings are padding to a block boundary. Careful: in the standard $u$ and $v$ are the padding lengths, while Menezes uses $u$ and $v$ for the blocklengths of $M$ and $A$. Same letters, different meaning — see the notation backup slide.

AES-GCM · the full scheme

Verify first, decrypt second

  • Bob recomputes the tag from what he received, then compares.
  • On mismatch he rejects, and the decryption never runs.
  • Menezes V5 p.19. The source's step 2 is authentication and step 3 is decryption, in that order, with "if $t' \ne t$ then reject".
  • Bob uses $L = L_A \| L_C$ — the length of the ciphertext, which equals the length of the plaintext in a stream cipher, so this matches what Alice computed.
  • The comparison must be constant-time. A byte-by-byte early-exit comparison leaks how many leading bytes were right, which turns a $2^{-128}$ forgery into a per-byte search. The source does not raise this; it is a standard implementation requirement.
  • Releasing unverified plaintext breaks the guarantee. Streaming APIs that return data before the tag is checked are outside the model.

AES-GCM · the sharpest edge

Reusing one IV hands over the key material

  • The same IV gives the same $J_0$, so the same pad twice.
  • XOR the two tags and the pad cancels.
  • What is left is the equation in $H$ that the pad existed to prevent.
  • Menezes V5 p.22, all four bullets, in the source's order. The source assumes $M_1$ and $M_2$ have the same blocklength and that the eavesdropper knows $M_1$.
  • Two separate disasters follow from one repeat. Confidentiality: the keystream repeats, so $C_1 \oplus C_2 = M_1 \oplus M_2$ and knowing $M_1$ gives $M_2$ — the slide-4 malleability, now for free. Integrity: the derivation on this slide gives $H$ and then the pad, so she can forge.
  • Why this is worse than it sounds: a 96-bit random IV collides after about $2^{48}$ messages by the birthday bound, which is reachable for a busy key. Counter-based IVs avoid it but break on VM snapshots, restarts and config cloning.
  • This is why AES-GCM-SIV exists: it derives the pad from the message as well, so a repeated nonce leaks only whether two messages were equal. Out of scope for the source deck; noted on the last backup slide.

AES-GCM · in practice

Seven properties worth knowing

  • It does both jobs — authentication and encryption — in one pass.
  • Authentication only is available by passing an empty $M$. That is GMAC.
  • Very fast on Intel and AMD, thanks to the AES-NI and PCLMUL instructions.
  • Both directions parallelize.
  • It can stream, processing data as it arrives.
  • Keys of 128, 192 or 256 bits.
  • It has a security proof — eventually. See the next slide.
  • Menezes V5 p.20, all seven, in the source's order.
  • On streaming: the sender can stream safely. A receiver that streams must not release plaintext before the tag verifies — see the decryption slide.
  • On GMAC: with $M$ empty, $u=0$ and $f_{A,C}$ reduces to $f_A$, which is the construction on slide 19.

  • Note what the table does not measure: a full AES-GCM encryption is roughly the AES cost plus the GMAC cost, and the table lists them separately.
  • ChaCha20 at 323 MB/s is the point of comparison for platforms without AES instructions, where it beats table-based AES.

AES-GCM · in practice

The proof took eight years to get right

  • NIST standardised the mode in 2007 — on a proof that was wrong.
  • The mode itself survived; only the argument needed repair.
  • Menezes V5 p.20, point 7: "The original McGrew-Viega security proof (2004) was wrong. The proof was fixed in 2012 by Iwata-Ohashi-Minematsu."
  • No attack came out of the broken proof. The flaw was in the bound's derivation, not in the construction, and the repaired bound is close to the original claim.
  • The moral the source leaves implicit: a standard's security rests on a proof that people have to check, and checking took eight years here despite very wide deployment.
  • This deck does not state the repaired bound, because that would need the IOM paper rather than the source deck. not sourced here

Summary

Five things to carry away

  • Confidentiality and authentication are separate; encryption alone is malleable.
  • Of the three generic compositions, only Encrypt-then-MAC is generically secure.
  • GMAC packs the message into a polynomial and evaluates it at a secret point $H$.
  • Guessing $H$ wins with probability at most $\frac{v+1}{2^{128}}$ — but one valid unmasked pair gives $H$ outright. The one-time pad $\mathrm{AES}_k(J_0)$ is what stops that.
  • Therefore: never repeat an IV. It cancels the pad and ends the key.
The thread through the whole deck: every guarantee in GCM reduces to "the pad is fresh", and the pad is fresh exactly when the IV is unique.

What this deck leaves out

  • The repaired security bound. Iwata–Ohashi–Minematsu (2012) fixed the proof; this deck states only that it happened, because the bound itself needs the paper, not the source deck. not sourced here
  • Nonce-misuse resistance. AES-GCM-SIV (RFC 8452) derives the pad from the message too, so a repeated nonce leaks only message equality instead of the key material. beyond the source
  • Tag truncation. SP 800-38D Appendix C allows 96–120 bit tags, and 32 or 64 bits only in restricted applications. Shorter tags weaken the forgery bound directly. beyond the source
  • Key commitment. A GCM ciphertext can be made to decrypt validly under two different keys. This matters for some protocols and is not part of the AE definition on slide 8. beyond the source
  • IVs that are not 96 bits. SP 800-38D hashes those through GHASH to form $J_0$. Only the 96-bit case is shown here.
  • Multi-user and multi-key bounds, and the cost of rekeying before the birthday limit.
